# 生活纪念品数字收藏项目定义与决策主文档

版本：0.12。更新日期：2026-10-15，Asia/Shanghai。状态：已接通本机前后端与真实浮雕生成、展示链路，最新交互要求改为总偏转最多 40° 与指针所在角落向下按压；继续逐页调整与功能完善，尚不代表完整产品交付或达到 95%。

本轮按用户最新授权在本机实现前后端分离，未 SSH 或部署远端。当前使用 FastAPI、SQLite 与本地媒体目录，前端 `127.0.0.1:4173` 调用后端 `127.0.0.1:8000`；PostgreSQL 仍是材料候选，并非用户硬指定。本地原图、收藏与持久生成任务已接通，详情通过 Three.js 展示真实 GLB 与纹理。生成采用 AnyImage 官方 MoGe2 ONNX CPU 推理及本项目浮雕网格、GLB 导出，未执行 Blender Bake Mesh；原技术链路与产品要求保留，实际验证范围见[本机后端与浮雕验证](本机后端与浮雕验证.md)。OCR、正式认证、云同步与 Android 原生近场传输仍未接入。

本项目以一张图片对应一件收藏，将票根、标签和生活照片整理成可回顾、可向附近朋友分享的数字纪念品。首页采用以图片和立体效果为主的收藏墙。本文合并开题报告与两份技术调研中的产品定义、业务规则、架构、协议、测试和风险，并维护用户通过 grill-me 作出的决定。原资料中的短视频和多素材建议保留为来源背景，不作为当前已确认的收藏单位。项目名称 MemoVerse 目前来自研究材料，尚未由用户确认。

移动端以用户于 2026-10-15 提供的五张图为视觉与页面结构依据：收藏首页、分类收藏、探索、朋友分享、我的。采用浅色中性背景、醒目黑色标题、浅灰搜索框和图片主导的卡片；底部为收藏、探索、中央添加、朋友分享、我的。原图已保存在 `docs/design-references/`，细则见第 15 节。D-036 至 D-038 已补充确认：探索采用社区推荐与预置主题推广，卡片可小范围晃动，按来源区分且暂不增加打卡状态。

账号采用邮箱与密码，注册验证邮箱并支持邮件重置密码；首次注册登录后使用，之后支持离线。退出保留本地数据，云端信息也继续保留；图片等大文件保存于对象存储，同时所有收藏始终保留完整本地副本。删除收藏同步到本人各端，清理缓存不删除云端收藏；普通缓存清理不得破坏完整的收藏副本。未上传成功的数据尤其不能提前清除。

当前阶段先做本地应用，用户要求尽可能完善、开发到 95% 以上，再由用户处理服务器和对象存储。这里的原型应接近完整可用产品，不能按纯页面或大量模拟功能交付。总体工作窗口约一个月，先用一周完成产品主要框架与内容，再按人分块快速迭代逻辑与 bug；不擅自将“95%”改写成已达到的完成度或精确到某天的保证。真机、服务器和对象存储配置调试后置。教师没有指定语言、Socket 或交付物等硬要求，评分规则由用户处理；当前不接受付费 API，Meshy 后议。

当前已经确认：范围由用户逐项裁决，允许修订开题；AnyImage 必须提供建模与浮雕效果，按最新 D-040 从正面向任意方向总偏转最多 40°，鼠标所在角落向下按压。首次保存或原图、视觉模板改变触发生成，纯文字修改复用模型；离线先保存二维图片，联网且服务可用后自动排队处理和补生成，不需要用户点击。Meshy 为可选增强，不列首版硬验收。Web 首版只要求在线使用。

识别与整理覆盖电影票、高铁票、饮品标签、购物小票和食物等非标签照片。离线不做语义路由，保留已确认的简单文字 OCR 和少量基础字段填写；联网后执行识别、语义处理和立体生成的自动流程。标签只做历史记录匹配：用户手填形成名字与标签记录，后续未填写标签时按名字做关键词检索，取命中记录中占比最高的标签；没有匹配就留空。用户修改只影响自己的收藏，已保存的其他收藏不联动改变。语言要求为简体中文与英文字母，其余资料共识仍是讨论基础，不因写入本文就成为用户批准的开发承诺。

## 2 产品目标与课程约束

来源：A §1、§2、§9；B p1–5、21–24；C p1–3、26–32、41。状态：除第 1 节决定外，资料共识待确认。

### 2.1 产品要解决的问题

目标场景是电影、旅行、饮品、探店等日常经历：凭证与影像分散，录入和归档麻烦；向朋友推荐时，一张截图缺少可以继续保存、标记和补充的结构化信息。这些是产品假设，需要通过实际使用验证。

候选产品主线为：采集现实素材，保存为个人收藏，辅助提取信息，形成有视觉表达的纪念品，再将一份内容和媒体齐全的推荐副本交给朋友。原材料希望接收者能够理解“是什么、为什么推荐、以后想不想体验”，并在真实体验之后建立自己的经历；当前按 D-038 仅保留来源区分，不将后半段实现为打卡状态或强制流程。

与普通图片分享相比，拟提供的价值是结构化信息、固定推荐快照、可继续整理的收藏关系、离线交付及后续同步。不能只用“支持 P2P 和三维”证明用户一定需要它。

### 2.2 不是哪些系统

三份材料均不将其定位为真实售票、验票或票券交易系统，也不要求唯一所有权、数字资产交易、NFT、防双花或共识账本。分享是复制与推荐，不是所有权转移。这里仍需用户确认最终产品边界，但这些功能不会因“票根”一词自动加入范围。

### 2.3 资源与课程目标

材料以 Web 与 Android、4 人、约 1 个月为背景。用户第七轮明确工作窗口为一个月，具体提交或答辩日期不清楚；先一周完成产品主要框架与内容，再每人负责一块迅速迭代逻辑与 bug。用户描述全程使用 gpt6Astra 和 Claude fable5.1 辅助开发，本文按其原称记录工具计划，不据此宣称已切换任何执行模型或调用外部服务。

用户确认教师没有指定技术或交付要求，只有评分规则，并明确无需助手了解这一部分。不再请求评分细则或将其作为启动条件。资料中的 1.30 仍保留为原开题目标背景，不当作得分承诺，也不据此增加用户未要求的功能。

当前本地开发以尽可能完善、达到 95% 以上为目标，再由用户处理服务器和对象存储（D-026）。不追问演示手机和服务器细节，不先调试对象存储。后续计划使用腾讯云 Linux 宝塔主机，具体配置约两天后确定；已有约 100 GB 对象存储资源和约 10m 带宽。上述信息来自用户描述，不代表完成部署或性能验证。

产品运行阶段当前不接受付费 API。OCR、识别与自动生成选型应满足该限制；Meshy 后续再议，当前不能以“可选增强”为由默认接入付费服务。该约束不等于要求另购设备，也不取消 AnyImage 的产品目标。

### 2.4 竞品与创新边界

A 提到 Movie Stubs、PocketStubs、TicketShelf；B、C 重点讨论后两者。材料中的产品说明已覆盖扫描票根、归档、照片、回顾、社交或 AI 视觉等重叠能力。因此不能把“OCR 数字票根”或“收藏册”写成独创。

材料提出的差异化是生活纪念品、离线结构化交付、接收后的推荐状态，以及推荐转为本人经历的连续关系；其中体验状态与转换流程不纳入 D-038 确定的当前界面。材料未证明市场绝无同类，也没有以安装实测或用户留存数据证明商业优势。

| 简单离线 OCR | 文字识别与少量基础字段自动填写，简体中文和英文字母；不承担语义路由 | **用户已确认 D-003、D-012、D-014、D-017**；具体字段和完成标准待定 |
| 联网识别与语义路由 | 处理四类票据及食物等无文字照片，将输入交给适用处理流程 | **用户已确认 D-011、D-017**；不要求无文字照片必须识别出文字或精确店名 |
| 历史标签匹配 | 用户手填提供名字与标签记录；未填时关键词匹配并取占比最高标签，无匹配留空 | **用户已确认 D-013、D-016、D-019 至 D-021**；个人修改不联动已有收藏 |
| 整理与来源 | 收藏册、筛选、基本搜索；按图区分我的经历与朋友推荐 | **用户已确认 D-038**：暂不增加想体验、已体验或打卡状态 |
| 首屏展示 | 最近收藏与分类横向卡片，图片和立体效果为主；分类页采用双列瀑布流 | **用户已确认 D-028、D-035**；不采用时间线或文件夹作为主首页 |
| 页面与导航 | 收藏、探索、中央添加、朋友分享、我的；提供分类收藏子页与搜索筛选 | D-035 确定结构，D-036 确定社区推荐与预置主题；不自动加入评论或好友系统 |
| 离线近场分享 | Android 两机发送元数据及所选本地素材；确认、拒绝、取消、验证、恢复、去重 | 资料共识待确认；支持机型和产品细节未定 |
| AnyImage | 建模与浮雕效果，从正面任意方向总偏转最多 40°；按输入变化自动生成 | **用户已确认 D-002、D-005、D-007 至 D-010、D-040**；新角度下的质量与交互待验证 |
| Meshy | 可选的 API 异步建模与结果归档增强 | **用户已确认 D-006**；不列首版硬验收，不等于已实现或已决定完全取消 |
| TripoSR | 单图三维重建候选 | 未被选定；仅作为研究参考 |
| 账号 | 邮箱与密码，注册验证邮箱、邮件找回；首次登录后可离线，退出不清数据 | **用户已确认 D-029 至 D-032** |
| 云端与同步 | 云端保留账号和收藏信息，图片等主要在对象存储，本地保留副本；Android 与 Web 同步 | D-031 确认存储方向，具体同步协议沿资料方案实现与验证 |
| Web | 首版仅要求在线使用 | **用户已确认 D-004**；不要求离线新增、编辑或浏览 |
| 故障与日志 | 识别、生成、上传、传输状态可见，错误可解释，可重试或恢复 | 资料共识待确认 |
| 删除与缓存 | 删除本人收藏同步各端；清临时缓存不删云收藏，也不破坏本地完整副本 | **用户已确认 D-033、D-034**；不影响朋友独立副本 |

以上表格描述项目功能方向。D-026 要求本地尽可能完整后再交给用户处理部署，因此不能把“先本地”理解为只实现页面或把自动生成全部长期留作占位。可在本地实现与验证的功能应真实运行，未接通或未验证的部分明确保留为未完成；云端部署和真机联调后置不等于取消分享、同步或自动生成。

一张图片就是一件收藏，不设计一次经历内的多图或视频合集。原资料涉及短视频、视频语义和多素材导入的内容仅保留参考，不自动加入当前实现范围；一张图片生成的缩略图、模型与纹理仍属于同一收藏的必要衍生资产。

首版暂不自动纳入 iOS、跨公网 NAT 穿透、多人 P2P 网络、全票种高准确识别、全视频语义分析、任意物体骨骼动画、复杂微服务集群或 MCP 主业务入口。这些在材料中被排除或列为远期，并非所有扩展都承诺在未来实现。原材料“不做公共社交信息流”的边界已被 D-036 针对探索的新决定修订：探索纳入社区推荐与预置主题推广，但不因此扩展为完整社交系统。

参考图的探索与朋友分享页面按 D-035 保留布局。探索按 D-036 参考社区中各点的曝光、受欢迎程度等组织推荐，也可推广预置主题，概念类似音乐推荐榜单。用户没有确认所有私密收藏默认公开，也没有确定复杂推荐算法；每个点是具体条目还是内容聚合尚未定义，不阻塞当前页面 demo。demo 可使用明确标记的示例社区数据，真实曝光与热度数据链以后接入。朋友分享可承载已有接收记录，不自动要求好友申请、关注、评论或聊天系统。

## 4 核心用户流程

来源：A §2.3、§5、§9.3；B p23–26、30–31；C p17–18、30–32。状态：资料合并提案，待确认。

### 4.1 无互联网创建

Android 拍照或导入单张图片后，为这张图建立一件收藏，先保存二维图片和基础记录。用户明确不要求离线语义路由；食物等没有文字的照片可以直接作为图片保存，不在离线状态下强制识别菜名、店名或类别。

已有简单离线 OCR 要求仍保留：有可识别文字时提取文字和少量基础字段，用户可以修订；此处不执行联网语义分类。具体字段和必填项尚未冻结。识别失败不阻碍图片保存。

联网后自动进入在线识别、必要的语义处理和建模流程。用户没有填写标签时，用名字检索已有用户手填的名字与标签记录，取命中记录中占比最高的标签，没有匹配就留空。不额外推理复杂标签，也不强行补齐店名、价格等大量详情。

### 4.2 生成视觉纪念品

首次保存收藏后自动执行 AnyImage，不需要用户主动点击生成。原图或视觉模板改变时自动重新生成，只修改标题、备注等文字时复用已有模型。生成的纪念品必须有建模与浮雕效果，并按 D-040 支持从正面向任意方向总偏转最多 40°。自动生成规则沿用 D-005、D-007、D-010，角度取代 D-008 的历史 20° 上限。

无网络或生成服务不可用时，先保存并显示二维收藏、记录待生成任务；联网且服务恢复可用后自动排队补生成，不要求用户重新点击（D-009、D-013、D-017）。具体重试时机、App 退出后的任务恢复和后台运行限制由工程验证确定。

生成状态、失败原因和恢复状态应可见。客户端区分二维预览、三维处理中和三维已就绪，不能将尚未生成的二维占位当成完成。Meshy 为可选增强，不自动随 AnyImage 的自动触发规则调用付费接口；是否将来自动调用 Meshy 尚未获用户确认。

### 4.3 当面分享

发送者选择分享字段与本地可用的媒体；双方确认设备和此次接收。先交付说明与预览，再传大素材。接收端区分“已看到信息”“正在接收”“已保存核心内容”“全部所选素材已齐全”。

中断后保留符合约定的进度；重连后验证对方、包版本和已有文件，继续缺失部分。校验完成后可靠导入并返回回执。何时算成功，以及可选大素材失败是否影响收藏成立，尚待裁决。

### 4.4 收到推荐与来源区分

A 看过电影后分享给 B，B 收到的是电影内容、A 的推荐快照及属于 B 的收藏关系，不自动获得“B 看过该电影”的经历。当前按 D-038 只区分来源，不增加想体验、已体验或打卡确认流程。原材料建议 B 在实际体验后创建 Experience 并关联推荐，保留为来源背景，不作为当前必做流程。

分享快照固定当时版本；A 后续修改评价或删除自己的收藏，不应破坏 B 已保存的副本。是否接收新版、是否保留历史并列版本，以及再次转发的默认范围未定。

### 4.5 恢复互联网

Android 提交离线操作与必要资产，自动排队进行联网识别和浮雕立体生成。用户看到的是一条自动处理流程，不需要分别启动 OCR、语义路由和建模。标签按历史名字与标签记录进行简单关键词匹配，用户已填写内容优先。

服务端幂等处理同步并检测版本冲突，客户端拉取增量；Web 在线访问收敛后的记录。所有收藏从创建时归属已注册登录的账号，不增加首次访客数据归户流程。主动退出保留本地副本和云端信息；再次访问遵循账号登录与数据隔离规则。

## 5 业务对象与术语

来源：A §5.1–5.3；B p2–3；C p16–18、24。状态：资料共识待确认，以下是概念模型，不是已经冻结的数据库 Schema。

| 对象 | 定义 | 必须区分的边界 |
| --- | --- | --- |
| Subject 内容对象 | 某部电影、店铺、饮品、线路等“是什么” | 同一内容可以有多次经历；同一车次编号也不自动等于同一趟乘坐经历 |
| Experience 个人经历 | 某用户在某时某地实际发生的体验 | 只能由用户主动记录或确认，不能由收到朋友推荐自动生成 |
| Snapshot 收藏快照 | 一次发布或分享固定下来的内容、推荐语、选定字段与视觉版本 | 源经历可编辑；既有快照不随源作者修改自动变化 |
| CollectionEntry 个人收藏条目 | 某个用户与纪念品的关系、来源和私人备注 | D-038 只区分来源，暂不加入想体验、已体验状态；材料中的状态枚举保留为背景 |
| Asset 媒体资产 | 原图、脱敏图、缩略图、GLB 和纹理等实际文件 | 内容相同不代表授权相同；远端对象键、本地文件和临时下载地址不能混用 |
| Transfer 传输记录 | 一次发送、接收、恢复及其状态 | 一次传输不等于一个收藏包；更换传输 ID 不应绕过业务去重规则 |
| SyncOperation 同步操作 | 一次有身份归属、基础版本和幂等 ID 的本地修改 | 重试同一操作不能重复执行；不是整份 SQLite 上传 |
| Job 异步任务 | OCR、视觉生成或其他后台计算的一次受控作业 | 任务受理、计算结束、归档成功和客户端可见是不同阶段 |
| Tag 标签 | 果茶、科幻、历史等填写在收藏上的分类词 | 用户手填的名字与标签用于后续关键词匹配；它与饮品包装上的标签图片不同 |

D-027 明确一张输入图片对应一件收藏。原图、缩略图、生成模型与模型纹理可以是多个文件，但它们是同一张图的衍生资产，不构成“多素材经历”。材料提出的 Subject、Experience 等后台概念不应强迫用户先建立复杂合集才能保存一张图片。

例如用户为自己的“霸气桃桃”填写“果茶”，数据库便有一条名字与标签记录。之后另一个用户遇到相同或关键词匹配的名字且未填写标签，就使用命中历史记录中占比最高的标签作为缺省值。数据来自用户实际填写，不需要单独管理一种词条对象。

### 5.1 标识与版本

候选标识包括 subject_id、experience_id、snapshot_id、source_id、source_version、collection_entry_id、asset_id、package_id、transfer_id、operation_id、job_id。它们的唯一性范围、重试生命周期和外部可见性应在协议与模型定稿时明确。

包表示本次冻结的分享内容与素材集合；传输表示传递该包的过程。相同快照选了不同素材是否形成新包，以及不同发送者转发同一快照如何去重，属于未决业务规则。

### 5.2 字段的来源和可信度

识别与补全字段应能区分用户手填、OCR、规则解析、第三方内容服务及模型推测。C 提出 value、confidence、source、confirmed_by_user 等信息。缺失或不可靠字段允许未知，不能为填满页面而虚构店名、日期、电影或商品。

用户已填写内容优先，未填写标签时采用 D-019 的历史记录关键词匹配结果，无匹配则留空。这里允许命中的历史标签作为缺省值，不使用凭空生成的默认答案。字段清单、日期精度、地点粒度和外部 ID 尚未确定；首版 OCR 语言已由 D-014 定为简体中文和英文字母。

## 6 离线能力与平台职责

来源：A §2–4、§7.1；B p14–15；C p7、14–15。Web 范围已由 D-004 裁决。

| 能力层级 | 条件与用途 | 当前解释 |
| --- | --- | --- |
| A0 本机离线 | 首次注册登录后，无互联网时在 Android 采集、编辑、保存二维图片、浏览本地素材 | 包含简单 OCR 和少量字段填写，不做语义路由或要求本机立刻建模；不是首次未登录即可使用 |
| A1 附近设备离线 | 两台 Android 无互联网，使用可用无线链路分享收藏包 | 无互联网不等于关闭 Wi-Fi 或蓝牙；目标设备及权限组合需实测 |
| A2 联网增强 | 注册登录、自动排队在线识别和立体生成、历史标签匹配、云同步及 Web 使用 | 账号从创建时明确归属；模型与任务实现继续验证 |

Web 首版仅在线使用。工程上可采用必要浏览器存储，但不将断网浏览、离线编辑或完整 PWA 列为首版验收。Android 的元数据、媒体、传输进度与离线操作必须分别考虑持久化，不能把缓存网页壳等同于实现本地优先。

### 6.1 账号访问与离线使用

首次使用先通过邮箱和密码注册、验证邮箱并登录（D-029、D-030、D-032）；提供通过邮件重置密码的完整流程。之后已登录设备在断网时仍可拍照、保存和使用已有本地内容。不新增首次匿名使用、访客收藏或登录后的归户产品流程。

主动退出结束账号访问状态，但不删除该账号本地缓存，也不删除云端信息（D-031）。结合首次登录后使用的约束，保留的数据仍按账号访问，不因文件还在设备上就向未登录状态或另一账号展示。凭据暂时失效与用户主动退出是不同事件；前者按已确定离线能力保留本地工作，云端操作等待恢复认证。

本地完整开发可由本地业务服务测试真实注册登录、验证凭据和密码重置流程，无需先部署腾讯云。开发阶段的邮件发送可连接本地测试收件服务，真实邮件服务配置后接；本地测试不能被表述为已向真实邮箱送达邮件。产品的验证和重置机制应真实实现，不能用假成功按钮代替。

## 7 总体架构提案

来源：A §3–4；B p11–16；C p14–16。状态：资料共识待确认，具体框架版本和部署资源未冻结。

候选架构为共享 React / TypeScript 界面，Web 在线访问；Android 使用 Capacitor 容器和 Kotlin 原生适配，承担本地库、文件、相机和近场网络能力。Three.js 展示视觉资产。当前先在本地推进产品原型，云端资源与 Android 真机联调不作为此阶段前置条件。

业务服务建议使用 FastAPI 与 PostgreSQL，采用模块化单体，异步计算交给独立 Worker，媒体进入私有对象存储。Redis、Celery 或其他队列工具按实际任务需求选择，不因为图中出现就自动增加全部依赖。

### 7.1 三条通信链路

1. **业务控制链路**：HTTPS API 处理账号、权限、收藏、同步和任务。WebSocket 或 SSE 用于状态通知；重连后通过查询恢复事实状态，推送不是唯一记录。
2. **媒体数据链路**：客户端获取限定对象、限定有效期的上传授权，直接向对象存储上传；业务 API 验证后登记。大文件不必完整绕经业务服务器。
3. **离线近场链路**：Android 原生模块承担设备连接与文件流，不经过云端。共享界面控制选择、确认、状态和进度，大媒体不通过 JavaScript 桥反复传 Base64。

### 7.2 边界与复用

Capacitor 提供 WebView 和原生桥接，不自动实现数据库、离线恢复、文件传输或 P2P。共享 UI 不表示所有平台功能相同。

传输业务应与发现和连接机制分离。协议状态机统一放在明确的一侧，避免 TypeScript 与 Kotlin 各维护一套互相漂移的协议。实际放置位置是工程决策，需根据文件流和恢复能力验证。

## 8 离线分享协议

来源：A §6；B p17–20；C p18–22、25。状态：语义提案一致，名称、线格式和成功边界尚未冻结。

### 8.1 连接路线

共同主线为 Android Wi-Fi Direct 建链后使用原生 TCP。A 进一步要求 TLS 和配对身份确认，后备为局域网或热点；B/C 推荐 Nearby 作为风险后备或第二适配器。这些候选不能累计解释为首版全部实现。

近场不要求跨公网 NAT 穿透。iOS、ICE、STUN、TURN 和跨公网 P2P 不属于当前已确认范围。是否支持无 Google Play services 的目标手机、是否自动发现及连接失败后的产品路径，需要明确设备条件后裁决。

### 8.2 消息语义

| 阶段 | 作用 | 草案中的代表名称 |
| --- | --- | --- |
| 协商 | 版本、能力与会话身份协商 | HELLO、HELLO_ACK、CAPABILITIES |
| 提议 | 展示标题、类别、预览、素材数和总大小 | OFFER |
| 用户响应 | 确认此次接收或拒绝 | ACCEPT、REJECT |
| 清单 | 固定快照、包与素材描述 | MANIFEST |
| 恢复协商 | 报告缺失资产及已持久化进度 | NEED_ASSETS、RESUME、RESUME_OFFSET |
| 数据传输 | 资产编号、偏移、二进制内容 | ASSET_DATA、CHUNK、TRANSFER |
| 验证 | 核对清单、类型、大小与哈希 | VERIFY、VERIFY_REQUEST、VERIFY_OK |
| 导入 | 满足约定条件后发布本地收藏 | IMPORT_COMMIT、COMMIT |
| 回执 | 告知导入结果，重复回执可安全处理 | RECEIPT |
| 异常 | 取消、拒绝、错误、中断和恢复 | CANCEL、ERROR、RESUME |

B 将协议命名为 MTP；C 建议 MSP，示例 magic 为 MVSP。以上名称仅反映来源，不意味着兼容实现三套枚举。最终应冻结一套版本化协议、字段、长度与错误码。

控制消息可采用有长度前缀的 JSON，素材采用二进制帧。接收端按帧解析，不能假设一次 read 对应一条完整消息。具体字节序、字段长度、最大帧长、分块大小及超时属于工程规格，不需要让用户挑选每个底层参数。

### 8.3 分享包

清单拟包含标题、类别、推荐语、来源快照版本、选定字段和资产列表。资产描述包含 ID、大小、MIME、哈希、优先级及是否必需。按当前单图收藏范围，素材主要包括原图或脱敏图、缩略图、生成模型和必要纹理。原材料中的视频传输是后续参考，不作为当前收藏输入的要求。

发送前核实所选文件实际在本机。只提供临时云地址不能证明离线可展示。优先发送元数据与缩略图，分别统计首次有意义内容出现时间和完整传输时间。

### 8.4 恢复与可靠导入

保存已持久化的连续偏移或分块进度；恢复时核对包、资产和对端身份，只传缺失部分。校验通过后再将临时素材与元数据变为正式可用状态。同包重复导入和重复回执不能造成额外条目，但“同包”的业务定义仍需裁决。

TCP 提供单次连接内的可靠、有序字节流。应用层恢复解决跨连接、进程重启、文件完整性及本地导入结果，不应宣称重新实现 TCP 的丢包重传。

C 允许所有必选资产完成后提交、可选资产继续传输；A 强调不能以信息已出现宣称全部保存。两者可以相容，但必须先定义当前单图收藏中原图、缩略图和模型的成功门槛。该问题在分享流程落地时确定，不重新引入多图视频合集。

### 8.5 安全会话

A 提出成熟 TLS 实现和通过二维码等带外方式核对公钥指纹；C 提出一次性配对秘密、二维码或短认证串。具体机制仍待验证，但不能把只显示同名设备当作安全配对，也不能以忽略证书校验代替身份确认。

哈希证明完整性，不证明发送者身份或文件授权。限制包大小、文件数量、媒体类型、路径和解包行为；原始照片、GLB 及其引用也属于外部输入。离线配对验证的是设备或会话，不自动构成在线实名认证。

## 9 同步与数据一致性

来源：A §7.2–7.3；B p15–16；C p22–24。状态：资料共识待确认。

本地业务修改和 Outbox 操作应在一致的本地事务边界内提交。操作携带 operation_id、实体 ID、动作、payload 和 base_revision，并绑定稳定的数据归属。恢复联网后先准备必要资产，再按依赖次序提交操作。

服务端按 operation_id 返回幂等结果，使用服务端 revision 检测并发更新，客户端按 cursor 拉取增量。不能单靠手机时钟选择赢家。D-029 已明确首次必须注册登录；A 中未登录即可新建的宽泛描述不再作为首次使用流程。首次登录后可离线，主动退出不清除本地或云端数据。操作、传输和任务结果始终归属创建它们的账号，不能在换号后转给当前登录者。

非重叠字段可以考虑安全合并；同字段冲突保留双方并提示用户。快照不可变，标签可考虑集合合并，个人经历采用版本检查。C 对 favorite 提出按确认 revision 处理，仍不能据此默许所有字段静默覆盖。

用户删除收藏应传播到本人账号各端（D-034）；删除使用 tombstone，防止旧设备的陈旧操作复活记录。迟到的 OCR、模型任务和上传回写应检查记录存在性和版本。朋友已经独立接收的副本不受原作者删除影响。主动重新收藏已删除的包，与旧同步自动复活不是同一行为，在相应分享流程中处理。

初版不因“离线同步”自动引入 CRDT。B 将 PowerSync 等现成方案列为参考；若使用现成同步工具，课程自主实现边界仍需准确说明。

## 10 识别与内容补全

来源：A §5.2、§8.4；B p6–7、23–24；C p7–8、37；用户决定 D-003、D-011 至 D-021。当前用户决定优先于材料中更广泛的补全建议。

### 10.1 当前确认的要求

简单离线 OCR 必做，最低成果是文字识别和少量基础字段自动填写。语言要求为简体中文与英文字母，不能扩大为繁体中文必验收或完整英文语义理解。具体字段、模型和准确率待样本验证。

离线不做语义路由；无文字食物照片先保存图片，联网再自动处理。标签自动填写仅使用历史名字与标签记录做关键词匹配，不使用复杂标签推理，不要求大量外部详情。有历史匹配时可以提供标签缺省值，无匹配则留空（D-019）。

### 10.2 候选处理流程

离线阶段先保存原图；对有文字的输入可进行简单 OCR 与少量字段填写，不添加离线语义分类要求。联网后自动排队处理图片，以在线识别和必要的语义路由提取或组织信息，再执行 AnyImage 立体生成。输入图像没有可识别文字时，不能把“OCR 必须成功”设为进入建模的门槛。

工程上应区分文字识别、语义处理、标签查询和三维生成：OCR 负责提字，AnyImage 负责既定的建模与浮雕。用户在描述中把它们统称为联网后自动将素材变成立体，本项目应提供这个统一体验，不将 OCR 本身表述成几何生成引擎。具体模型、依赖顺序和并发策略由实现验证确定。

材料推荐 Android ML Kit 的 bundled 模型来支持首次使用时离线识别；最终需要验证目标系统、语言模型、包体与无网络首次启动。在线使用更准确识别模型的方向已经明确，但 PaddleOCR、云 OCR、VLM 或其他具体方案尚未选型。

### 10.3 类别与事实边界

用户要求简单语义路由覆盖电影票、高铁票、饮品标签、购物小票，以及食物照片等非标签输入（D-011）。这是当前范围，不再限制为助手此前建议的三类；它也不等于每类都要完整字段提取或深度知识查询。

| 输入类别 | 当前要求 | 未被要求或尚未决定的内容 |
| --- | --- | --- |
| 电影票 | 文字与基础字段，联网分类；支持科幻、历史等题材标签的补充方向 | 精确匹配片库、海报、演职员等大量信息不是自动承诺 |
| 高铁票 | 纳入语义路由与基础字段处理 | 完整乘客、座位、订单字段并非已确认验收项 |
| 饮品标签 | 从识别信息关联分类标签；用户以霸气桃桃对应果茶举例 | 不保证仅凭任意名称确定品牌、配方或全部商品详情 |
| 购物小票 | 纳入简单路由与基础处理 | 全部商品逐行识别、金额校验和消费统计未被要求 |
| 食物等无文字照片 | 离线先保存图片，联网进入自动处理与立体生成 | 不要求离线识菜，不强制确定精确菜名或店名 |

没有可见文字、定位许可或其他上下文时，一张食物照片不能可靠确定精确店名。缺少可靠证据就保留待补充，不将推测写成已确认事实。人工修改优先于未经确认的后续自动结果。

### 10.4 历史标签匹配

当前规则以第六轮的 D-019 至 D-021 为准：

1. 用户为自己的收藏手动填写名字和标签，这些记录存入数据库。
2. 后续用户未填写标签时，以当前名字检索历史名字与标签记录，进行简单关键词匹配。
3. 有匹配时，取命中记录中占比最高的标签作为缺省值；用户仍可自己修改。
4. 没有匹配时，不设标签，不调用模型猜测新标签。
5. 用户修改只改变自己的收藏；数据变化只影响以后自动补全，不联动改写其他已保存的收藏。

例如已有用户给“霸气桃桃”填写“果茶”，后续用户使用相同名字且不填写标签时，可以匹配得到“果茶”。这里不额外设计词条编辑、公共对应关系、审核入库或历史批量更新功能。

### 11.2 AnyImage 链路

材料提出输入图片、选择模板或主体、执行 AnyImage、必要的几何与材质烘焙、导出、资产检查、归档，再由 Three.js 展示。目标是在最终 Web 和 Android 中保留视觉外观，不能仅凭 Blender 内显示正确判定交付成功。

重点验证自动化入口、无界面执行、交互选区处理、热 Worker、作业隔离、超时回收、UV 和贴图导出、模型体积及手机表现。服务器或个人电脑均为材料中的执行候选；地点和资源未确认。

不能因为 AnyImage 已选定就承诺一秒完成，或承诺从单张照片真实还原所有不可见表面。效果必须通过用户认可的代表样例明确。

用户观察到 AnyImage 在 10–20° 内几乎不会失真，这作为选择该路线的依据保留；它不是本项目在目标图片、设备和导出流程上的实测结论。验收需在最终前端和约定角度内检查建模、浮雕、贴图及边缘表现。

自动生成采用当前单张输入图片对应的任务。首次保存及原图、视觉模板变化触发，纯文字修改不重建；任务去重、旧输入任务的取消或结果隔离、失败后的恢复属于需要验证的实现细节。D-027 已收束输入单位，不为当前版本增加视频抽帧或多图建模输入要求。

### 11.3 Meshy 链路

Meshy 已由 D-006 定位为可选增强，不列首版硬验收；D-025 进一步明确当前不接受付费 API，Meshy 后续再议。因此以下仅保留未来接入的技术参考，当前不据此实施付费调用：建立持久 Job，记录 external_task_id，跟踪状态，完成后下载和归档，再发布 ready。

不将外部临时 URL 当作永久模型地址。超时后先核查已有提交记录，避免重复创建付费任务；预算、额度、并发、失败退款和重试规则需按实际服务验证。

### 11.4 动态与性能口径

用户最新 D-040 将从正面向任意方向的总偏转上限改为 40°。工程应约束相对正面的总偏转，而不是把水平、垂直两个 40° 上限叠加。鼠标在哪个角落，就压下哪个角落；用户确认左右方向现已正确，上下反向需修正。触控细节随页面调整验证。

材料中还讨论了悬浮、翻面、卡片展开和光照等效果；它们仍是候选，不因出现在材料中自动成为要求。当前 40° 边界不构成必须支持绕背或 360° 查看，也不自动包含骨骼动画。

分别记录请求发出、任务受理、排队、Worker 开始、预览可见、计算完成、归档完成和客户端加载完成。冷启动与热启动单列；首次可见与最终完整模型是不同指标。

A/B 将约一秒列为待验证目标；C 新增 API 受理小于 500 ms、快速预览小于 1 s 等建议。它们未成为用户确认的性能承诺。

## 12 Worker 调度与执行资源

来源：A §3.3、§8；B p26–28；C p9、15、33、37。状态：工程提案待验证。

优先考虑个人电脑 Worker 主动向云端建立受认证的出站连接领取任务。若使用隧道，只开放受限任务接口，不暴露桌面管理或任意命令入口。电脑离线时任务排队或显示暂不可用，基础收藏继续可用。

## 13 媒体存储与权限

来源：A §7；B p13–14、28；C p12–16、24–25。状态：资料共识待确认。

云端数据库保存用户、收藏、权限、引用、任务、版本和同步记录，候选实现为 PostgreSQL；对象存储保存原图、脱敏图、缩略图、模型与纹理等大文件。用户确认图片等主要保存在对象存储，本地为备份（D-031），并进一步要求所有收藏始终保留完整本地副本（D-033）。Android SQLite 与文件目录支持离线记录、操作队列和传输进度；服务器临时目录可重建，不作为唯一归档。

材料共同倾向腾讯云 COS。OSS 与 AWS S3 是替代候选，S3 兼容 API 是接口概念，不是要求部署另一套存储。用户已说明后续腾讯云主机和约 100 GB 对象存储资源；具体区域、存储接入配置和 SDK 等待后续部署阶段处理，不阻塞本地原型。

### 13.1 上传发布

流程建议为申请限定上传授权、客户端直传、服务端核实大小与归属及完整性、资产标记 ready、收藏引用资产。数据库和对象存储不天然共享原子事务，应以可恢复状态和未引用临时对象清理处理失败。

数据库保存稳定 object_key，访问时获取短期授权；永久云密钥不进入 APK 或浏览器。资产记录至少需要类型、大小、哈希、存储位置、所属空间及引用关系，具体字段待设计。

### 13.2 独立副本

文件内部去重不等于共享授权。接收者同步离线副本时，可以重新上传本地文件，或在授权成立时复用已有资产；不能仅凭哈希读取其他人的私有文件。

原作者删除自身记录不能破坏已导入副本。删除物理对象前要考虑仍有效的引用。原账号注销、转发来源及重新上传策略需要在实现中覆盖；D-029 已排除首次匿名使用，不再将匿名发送列为当前硬要求。

### 13.3 本地保留与缓存

用户确认所有收藏始终保留完整本地副本；退出后仍保留，云端也继续保留用户信息和对象存储中的媒体。这里的“缓存和备份”不能解释为只保留最近浏览内容，或空间不足时自动淘汰收藏原图与模型。退出账号不等于清缓存、删除收藏或删除云端数据。

需要区分两个存储阶段：未上传成功的原图和离线修改目前只有本地可靠副本，必须保留到同步完成；已经成功归档云端的素材才具备从云端重新取得副本的条件。这是实现离线不丢数据的必要约束，不因为用户称它为缓存就提前删除。

第十轮同时确认两条规则：完整收藏始终保留本地，以及清理缓存只释放本机空间、不删云收藏。为同时满足它们，工程实现将普通缓存清理限定为临时文件、任务中间结果及重复处理残留，不删除组成完整收藏的原图、模型和必要纹理。这是两项决定的配套实现解释，不是另一次用户要求删除本地收藏。

删除收藏是独立操作：删除本人账号各端的该收藏，朋友已收到的独立副本不受影响（D-034）。文件删除仍遵循有效引用规则，不能误伤其他收藏需要的资产。

从云端同步下来的收藏，必要素材尚未下载完成时，应展示实际同步状态，不得宣称已完整保存在本机。空间不足时报告未完成并保留已有内容，不静默违反完整副本要求。Web 继续按 D-004 仅要求在线使用，不因本地副本策略新增 Web 离线验收。

## 14 隐私与分享边界

来源：A §5.3、§6.4、§10.1；B p25、28–29；C p25、31–33。状态：资料共识待确认。

材料建议分享字段白名单，默认排除原始票据、二维码、订单号、座位及不必要个人信息；原图单独选择。需明确脱敏是在发送副本上完成，原始收藏如何保留，以及自动脱敏失败时的确认流程。

已经离线交付的内容不能承诺远程强制收回。应用内是否允许再分享、来源如何显示，以及收到的推荐如何关联人物，需要产品裁决；不能将设备配对冒充实名身份验证。

第三方海报、模型和外部资料需保留来源、许可和署名信息。开源代码、插件、模型权重及生成资产的许可可能不同，实施前按实际采用版本核实。课程演示不自动等于可以任意再分发素材。

### 15.2 共同视觉规则

- 白色至极浅中性背景；主要颜色来自照片。大标题近黑且醒目，辅助信息用灰色，保持充足留白。
- 搜索栏为浅灰胶囊形；头像圆形，顶部保留信封入口。未读提示只使用小面积红色。
- 图片主导，圆角与阴影轻。横幅、竖版电影图、方形生活图及横向票根保留合适比例，不统一裁成相同尺寸。
- 最近收藏与月份回看使用白色相片边框、轻微叠放的实物感；纸张效果集中在相片卡，不把整个界面改成厚重手账。
- 名称贴近图片，标签、日期、来源和数量使用次级文字；以间距、对齐和字重组织内容，不增加重复的大色块外框。
- 图标保持统一线性语言，选中导航用近黑实心或强调态，未选中用灰色；中央加号为圆形创建入口。
- 浅色方向已确定。字体和间距数值在还原时按中文可读性与参考图接近度落实，不另套深色或营销页面模板。

### 15.3 导航与层级

底部五个位置为收藏、探索、中央加号、朋友分享、我的。加号是创建操作，不是空白一级页面。收藏首页进入分类页与单件详情；分类页提供返回收藏。各一级页面有对应选中态，底栏与页面正文为设备安全区预留空间。

横向滑动只出现在参考图的卡片轨道内，不导致整个页面横向溢出。搜索、筛选、排序、类别箭头、头像、返回和信封都以真实控件实现，不将整张截图铺成不可操作页面。未提供参考的登录、添加、详情、接收确认与设置子页沿用同一视觉语言。

### 15.4 五个页面

**V1 收藏首页**

头像、搜索收藏与信封位于顶部；下方为我的收藏标题与真实总数。最近收藏使用大横向图片卡片，随后按电影、日常等分类展示横向轨道。分类标题带进入箭头及真实件数，图片下显示名称、分类或日期。主内容为收藏展示，不转成数据仪表盘。

**V2 分类收藏**

顶部包括返回、分类名称、件数、最近添加排序和分类内搜索。来源筛选为全部、我的经历、朋友推荐；下方为双列瀑布流，按图片自身的适宜比例展示电影图、票根和生活照片，配名称、日期与轻量来源标记。

我的经历与朋友推荐是来源区分，不等于想体验与已体验。D-038 已明确按图只区分来源，暂不增加打卡状态或每张卡的体验进度。

**V3 探索**

顶部搜索主题与纪念品，提供精选、电影、旅行、日常、展览等入口。内容依次为大主题卡片、较小横向卡片轨道和带缩略图的更多主题列表。主题是内容组织方式，不改变一图一收藏的单位。

内容按 D-036 来自搭建的社区，可参考各点的曝光、受欢迎程度等形成类似音乐榜单的推荐，也可采用预置主题选题推广。每个点的条目或聚合粒度尚未定义，demo 先使用明确标记的示例社区数据和预置主题；真实曝光、热度数据链后续接入。不据此默认公开私密收藏，不推定复杂推荐算法或评论、好友系统已经确定。展览等栏目文字不自动增加一个必须实现的专门 OCR 票种。

**V4 朋友分享**

顶部搜索朋友或收藏，提供全部与未查看筛选及真实数量。最新收到使用带分享者头像、昵称、时间和推荐语的大图；最近分享为双列卡片，更早记录为紧凑列表。

这个页面可由已有近场接收记录提供数据，搜索朋友可按记录中的分享者名称筛选。图示不自动要求好友申请、关注和聊天系统。书签的具体收藏动作、信封中的通知类型在已有接收与任务流程中落实，不能仅凭图标推断自动收藏或即时聊天。

**V5 我的**

资料区显示头像、昵称、简介、编辑资料，以及真实收藏和分类数量。下方为最近收藏横向轨道、按月回看的相片叠放卡片，以及收藏管理、账户与同步、设置与隐私入口。

按月回看是单图收藏按时间聚合，不建立多素材收藏对象。头像、小宇、86 件、4 个分类和日期等均为示例；真实页面由账号和收藏数据驱动。

### 15.5 三维与交互检查

AnyImage 建模与浮雕必须真实生成，卡片阴影或 CSS 倾斜不能代替模型。D-037 确定卡片晃动，D-040 最新将浮雕总偏转上限改为 40°，并要求指针所在角落向下按压；保留正确的左右方向、修正上下反向。触控细节与新角度下的边缘表现仍需验证；卡片动效不标为真实三维已就绪。

还原时采用以下工程检查：图标和按钮具有足够触控范围与可读标签，手机不依赖鼠标悬停；键盘焦点可见；底部安全区无遮挡；加载、失败和生成状态清楚；尊重减少动态效果设置。图片预留比例以避免跳动，三维资产按可见性和实际交互加载，避免整面收藏持续重绘。

通用设计库没有直接匹配这组移动端收藏页面的模板，因此视觉以 V1–V5 为准，触控和可访问性仅采用通用检查，不套用摄影工作室或落地页设计。

### 15.6 配套流程与真实数据

注册与登录实现邮箱、密码、验证及重置；添加页负责单图拍照或导入及必要修订；详情展示原图、信息与二维或三维状态；分享和接收页展示对方、确认、进度、取消与恢复；账户与同步、设置与隐私遵循已确认的数据规则。

已识别、已确认、已保存本机、已同步、媒体齐全和三维可用分别由真实状态驱动。截图中的 86 件、24 件、32 件、未查看 3 条等不作为固定业务值。空状态、处理中、错误与无匹配标签均需正常展示。

桌面 Web 延续同一视觉语言和页面语义，按宽屏适配，不将手机截图拉伸铺满。具体桌面布局由实现验证，不改变本轮确定的移动端结构。

### 16.1 测量口径

网络分别统计发现成功率、连接耗时、首个有意义内容时间、完整传输耗时、吞吐、恢复成功率和文件校验结果，报告测试设备与样本量及中位数、P95。

A 提出约 5 MB 图片包与约 50 MB 媒体包；C 另提 100 MB 连通性实验和前 48 小时多个设备组合。用户已决定本地原型优先，因此这些保留为后续测试参考，不再把前 48 小时实机实验列为当前阶段的前置条件。

识别按类别统计字段准确性与人工修正耗时；C 提出电影票、高铁票、饮品贴纸、菜单小票各 10 张作为试验样本。最终测试集由首版类别决定，不能只用一张清晰样例代表整体质量。

三维统计受理、排队、计算、归档和首屏加载，区分冷热、硬件、图像大小、模型大小和失败率。C 提出的发现成功率至少 95%、首屏约 1–2 秒等目标未被用户确认，必须先明确测量条件。

## 17 开发与交付方式

工程解释：文字识别与 AnyImage 建模承担不同职责，用户所要求的是联网后统一自动完成的体验。具体在线模型未选择，不能把用户对整条流程的口语描述写成“OCR 自身直接生成三维几何”。

用户原话：“没有可靠信息就留空，不自动填默认值（推荐）”

确定：不强制填满字段，不以凭空生成的答案代替缺失信息。第六轮 D-019 进一步明确，有历史匹配时允许该标签作为缺省值；无匹配时不设标签。这不是禁止一切默认填写。

### 20.7 第六轮 标签匹配的纠正与收束

确定：用户手动填写自身收藏便产生名字与标签记录；后续记录通过检索这些历史数据获得缺省标签。用户修改只改变自己的收藏，不需要额外词条对象、共维界面或公共修改操作。D-015 的旧解释不再生效。

**D-021 不联动修改历史收藏**

确定：不存在单独管理的共享库产品。其他已保存收藏保留当时的标签；历史数据变化只影响之后的自动补全。无需再就公共词条维护或历史批量更新追问。
