创建日期：2026-10-20。基线：`main` `eb486c9`。产品规则以[主文档](项目定义与决策主文档.md)为准；本文只写执行顺序、工作包与验收。

## 0 阅读顺序

1. `AGENTS.md`；修改 Web 时加读 `demo/AGENTS.md`。
2. [主文档](项目定义与决策主文档.md)、本计划、[API 约定](local-api-contract.md)。

## 1 执行规则（硬性）

1. 每个工作包一个分支（`codex/wp-NN-<短名>`）、一个 PR；按逻辑单元提交，不 amend、不强推。依赖的 PR 未合并时，从依赖分支创建新分支，PR base 设为该分支，上游更新用 merge 同步。修改 schema 的工作包（WP-01、03、04、05、07，以及需要改 schema 的其他包）不并行，按完成顺序递增版本号，各自附迁移。
2. 每个工作包是一个大阶段：PR 前按交付技能完成子代理审查与格式整理；创建 PR 后可以开始下一个包；CI 失败与 Codex 审查意见在原分支追加提交修复。
3. 注释只写代码无法表达的约束；不写解释代码在做什么或本次改了什么的注释。
4. 不提交临时脚本、调试输出、截图与本地产物；一次性脚本放 `.cache/`，完成后删除。
5. 除本计划指定外不新增文档。接口变化更新 `docs/local-api-contract.md`，模块职责变化更新对应 README 的责任地图，修改的文档标注更新日期。产品规则需要变化时先停下请用户确认，确认后再更新主文档。
6. 测试断言真实行为。只允许替换外部网络服务（Cognito、TMDB、维基百科；对象存储用现有本地实现），以及沿用现有约定、需要模型权重的推理步骤（真实推理测试按现有开关单独运行）。不用模拟成功代替功能。
7. 不加兼容映射、别名或兜底补丁，优先修正调用逻辑。schema 变更写显式迁移，不静默接受旧结构。
8. 密钥只进环境文件（服务器 `/etc/memoverse.env`、本机受限文件），不进 Git、日志或前端。
9. 不部署、不合并、不启停 EC2，不修改 AWS、Cognito 或 Google 控制台配置，不注册第三方账号、不申请 API Key；需要时写进 PR 描述交给用户。
10. `Backend tests`、`Frontend tests`、`deployment-recovery` 必须通过；WP-10 新增 `Android tests` 后同样必须通过。
11. 计划与代码、文档或用户新指令矛盾时，停在受影响步骤并报告用户，不自行选择。主文档未覆盖的产品行为同样停下询问，不自定规则。
12. 验收分“自动化”与“用户真机”两类。自动化项必须在 PR 中通过；需要真机的项写成测试清单交给用户，不在未验证时宣称完成。
13. PR 描述列出：已完成的验收项、未覆盖项、需要用户执行的操作（配置、部署、真机验收）。

## 3 现状要点（`main` `eb486c9`）

- 后端调用链：`app.py` 装配 → `api.py` HTTP → `services/` 业务 → `store.py`（SQLite schema 2，`require_schema2_root` 拒绝其他版本，`app.py` 与 `generation/observability.py` 也检查 schema 2）。`state.py` 返回账号全量快照。
- 账号有单调递增的 `users.revision`；收藏有 `version`，PATCH/DELETE 版本不符返回 409；Web 的 PATCH 提交整条内容；删除是硬删除，没有墓碑，也没有增量接口。
- 鉴权是 BFF 模式：`auth.py` 加密保存 Cognito 令牌，浏览器只持有不透明会话 Cookie（7 天）；写请求校验 Origin、`X-MemoVerse-Client: web` 与 `X-CSRF-Token`。Google 登录走 Cognito 托管页与 PKCE，回调固定为网站 `/api/auth/callback`。
- 生成：`jobs.py` 单线程 `JobWorker` → `generation/repository.py` 领取 → `generation/pipeline.py` 下载原图、调用 `relief_engine.py` 子进程（`anyimage_worker.py`）、上传 → repository 发布并核对输入版本。重型依赖（onnxruntime、trimesh）由 `scripts/setup-anyimage.*` 固定安装在 `.cache/anyimage-deps`，缺失时相关测试跳过。
- `services/collections.py`：`infer_tag` 只匹配本人记录；`update` 在 `art` 改变时也会重新生成。`demo/src/data.ts` 另有一份只供测试使用的 `inferTag`。
- 展示分类 `contracts.py::Category` 为 `movie`、`travel`、`daily`、`exhibition`（电影、旅行、日常、展览）。`CollectionFields` 与 `UpdateCollection` 要求标题、分类、日期必填；Web 表单（`useCollectionDraft.ts`）默认分类为 `daily`、日期为今天。
- 对象：图片 `media/<sha>.<ext>`，模型 `models/<id>/{model.glb,depth.npy,geometry.json}`，由 `template.validate_model_outputs` 校验；查看器的相机参数来自 `geometry.json`；EC2 角色只允许读写 `media/*`、`models/*`。`collect_item`、`generation/repository.py`、`backups.py`、`state.py`（模型与原图不一致时返回 409）与 `template.py` 假定模型属于收藏原图。
- 服务器发布时 `deploy/ubuntu/install.sh` 调用 `scripts/setup-anyimage.sh` 安装推理依赖。
- 初始模板：`MEMOVERSE_TEMPLATE_DIR` 下 manifest 加 SHA 校验（`template.py`），文件不入 Git。模板复制的收藏没有显式来源标记。
- 尚无 OCR、海报、徽章与 Android 工程。

## 4 工作包

每包列出：目标、依赖、修改范围、约束、验收、不做。开工前先核对所列路径，与现状不符时按规则 11 处理。新增或改变的收藏字段、派生资产，都要出现在 `state.py` 快照与同步拉取结果中。

### WP-01 服务器同步接口

- 目标：App 离线修改联网后能幂等上传、合并，并增量拉取服务器变化（收藏与个人资料）。依赖：无。
- 范围：`store.py`（schema 3 与显式迁移：变更序号、墓碑、已处理操作）、`app.py`、`generation/observability.py`、新增 `services/sync.py`、`api.py`、`contracts.py`、`backups.py`、`scripts/restore-account-backup.py`、API 约定、`backend/README.md`、`deploy/ubuntu/README.md`（回滚须恢复迁移前副本）。
- 约束：
  - 迁移在应用启动时于单个写事务内逐级执行，执行前用 SQLite backup API 在数据目录保存副本；schema 版本号常量只定义一处，所有检查点引用它。
  - 拉取 `GET /api/sync/changes?cursor=`：返回游标之后的收藏与资料变化、墓碑及新游标；游标使用账号级单调序号（可基于 `users.revision`），不用时间戳；收藏复用 `state.py` 的序列化函数。
  - 上传 `POST /api/sync/operations`：批量操作 `{operationId, entity, entityId, action, changes}`，`changes` 只含改动的字段；同一 `operationId` 重放返回首次结果。
  - 合并按主文档 3.9：服务器按收到的先后逐字段应用，同一字段后到覆盖先到；每次应用递增收藏 `version`，返回应用后的服务端值。
  - 删除写墓碑；针对已删除实体的后续操作返回“已删除”，不复活记录。
  - 新建复用现有草稿 ID 幂等与 `POST /api/media` 上传；同步新建与 Web 新建调用同一业务函数，同样触发生成。
  - Web 写入、生成完成与识别结果发布也产生变更序号；Web 现有接口行为不变：Web 仍提交整条内容并按版本号返回 409，与 App 同改一件收藏时，重新读取后以 Web 保存的整条内容为准。
- 验收：同一操作重复提交不重复创建；删除后旧设备的修改不复活；两台 App 设备改不同字段时都保留，改同一字段时以后到的为准；游标拉取不漏不重；跨账号访问被拒绝；在现有数据副本上 schema 2→3 迁移成功，失败时原库不变；备份与恢复包含新表。
- 不做：CRDT、实时推送、整库上传、分享同步（WP-14）。

### WP-02 App 鉴权接口

- 目标：Android 不依赖 Cookie 完成邮箱登录、注册验证、找回密码与 Google 登录。依赖：无。
- 范围：`backend/auth.py` 及其测试、API 约定、`backend/README.md` 配置表。
- 约束：
  - App 请求带 `X-MemoVerse-Client: android` 与 `Authorization: Bearer <会话凭据>`；凭据与 Web 会话同表、同有效期与刷新逻辑，由响应体返回，不设 Cookie。
  - Bearer 请求不做 Origin 与 CSRF 校验；Cookie 请求保持现有校验；同一请求携带两种凭据时拒绝。
  - 登录前的鉴权请求（登录、注册、验证、找回密码、Google 交换）带 `X-MemoVerse-Client: android` 时不校验 Origin、不设 Cookie，凭据放在响应体返回。
  - Google：App 生成 PKCE、state 与 nonce，经 Custom Tabs 打开 Cognito 托管页并回调到 App 重定向地址；后端新增交换接口，用授权码与 verifier 换取令牌、校验 nonce 后建立会话。允许的重定向地址来自环境配置；默认复用现有无密钥客户端，由用户在控制台添加回调地址。
  - 退出时撤销会话与上游刷新令牌，与 Web 一致。
- 验收：Bearer 请求只能访问本人数据；缺失或伪造凭据返回 401；Cookie 请求缺 CSRF 仍返回 403；混用凭据被拒绝；交换接口拒绝错误 verifier、错误 nonce 与未登记的重定向地址；令牌与授权码不出现在日志。
- 不做：WebView 登录；在 App 内保存 Cognito 令牌。

### WP-03 生成触发与标签匹配修正

- 目标：`art` 不再触发生成（D-051）；标签匹配跨用户并排除模板记录（D-049、D-059）。依赖：WP-01（schema 串行）。
- 范围：`services/collections.py`（`update` 的重建条件、`infer_tag`）、`store.py`（记录收藏是否为用户新建、标签是否手填；模板复制与朋友推荐的收藏不计入）、后端测试、API 约定、`demo/README.md` 的触发说明；删除 `demo/src/data.ts` 的 `inferTag` 及其测试。
- 约束：保持现有关键词规则与“占比最高、无命中不设标签”；统计口径与匹配时机按主文档 3.5。迁移时 ID 在模板清单中的记录标为模板；其余来源为“我的”且标签非空的记录视为手填。
- 验收：只改 `art` 不新建任务、模型不变；换图仍新建任务；A 手填的标签能被 B 新建的同名收藏命中；模板记录不计数；B 修改标签不改变 A 的记录；已保存的收藏不随后续数据变化；标签为空时用户之后补填标题会匹配一次。
- 不做：类型与关键识别字段触发（WP-04 类型、WP-05 海报、WP-07 徽章、WP-08 节日各自接入）。

### WP-04 服务端 OCR、自动分类与字段提取

- 目标：保存图片后自动识别文字、判断类型，按主文档 3.4 的表填写字段、标题、收藏日期与展示分类；用户可修改类型与识别字段。依赖：WP-03。
- 范围：生成 worker 增加识别阶段（`jobs.py`、`generation/`、新识别模块与子进程入口）、`contracts.py`（票据类型、识别字段与来源；创建与更新契约允许标题、分类、收藏日期为空）、`store.py` 迁移、`state.py`、`backups.py`、OCR 依赖安装与校验（扩展 `scripts/setup-anyimage.*`，不新增脚本）、`THIRD_PARTY.md`、`demo/src/features/collections/`（识别状态、类型与识别字段的展示和编辑）、`demo/src/data.ts` 的快照校验、API 约定。
- 约束：
  - OCR 使用免费 CPU 引擎（如 RapidOCR / PP-OCR ONNX），固定版本与权重 SHA；按 `relief_engine.py` 的子进程方式运行，在同一串行 worker 中执行，不与 MoGe2 并发。
  - 自动分类是纯函数：输入 OCR 文本行，输出类型与字段；关键词规则在代码中，可单测。
  - 识别结果用独立短事务发布（先于浮雕），核对输入版本；只填空字段或来源为离线识别的字段，并记录来源；换原图时替换来源为识别的字段，保留用户填写的字段。
  - 标签为空且标题由识别填写时，在识别结果发布的同一事务中按主文档 3.5 匹配标签。
  - Web 新建表单只要求图片；不预选分类、不预填日期，只有用户点选或输入的值算用户填写；卡片显示“识别中”，识别后标题仍为空时显示“未命名”。
  - 编辑页可修改票据类型与识别字段，用户修改的字段来源记为用户；修改类型后重新执行识别（用户填写的字段保留）并按新类型重新生成。
  - 已有收藏不补跑识别。
  - OCR 全文不持久化、不写日志；白名单字段之外的内容（姓名、证件号等）丢弃。
- 验收：用户提供的真实样例（第 5 节）每类至少 3 份转写为 OCR 文本夹具，电影票、交通票、饮品标签、购物小票的类型、字段、标题与分类正确（样例图片不入 Git）；景区与展览门票、无文字图片归为其他、分类为日常并照常生成浮雕；只传图片的新建成功，默认值不会挡住自动分类与日期填写；识别失败不阻止保存与生成；识别期间用户的编辑不被覆盖；修改类型后按新类型重新识别；识别填写的标题能命中标签；同步拉取包含类型、识别字段与来源；数据库与日志不含姓名、证件号；在本机测量 OCR 子进程与应用进程的峰值 RSS 之和写入 PR（作为估算），超过服务 `MemoryMax=1500M` 时停下报告。
- 不做：AI 分类、付费 OCR、Android 离线 OCR（WP-12）。

### WP-05 电影海报

- 目标：电影票按片名取得海报，作为封面与浮雕输入。依赖：WP-04。
- 范围：新海报模块（TMDB、维基百科客户端与选择规则）、`store.py`（海报缓存：来源与影片 ID 对应图片资产）、生成流水线、`state.py`、`backups.py`、`collect_item`、前端卡片与详情、API 约定、`THIRD_PARTY.md`（TMDB 署名要求）。
- 约束：
  - Key 从环境变量 `MEMOVERSE_TMDB_API_KEY` 读取；缺失时只用维基百科。
  - 匹配规则按主文档 3.6（规范化片名完全一致；上映日期不晚于放映日期且最接近）；无可信匹配时用票的照片。
  - 下载的海报经 `media.py` 同样的格式与尺寸校验，作为不可变图片资产存入现有 `media/` 前缀（不新增 S3 前缀，避免改 IAM）；同一影片跨账户复用文件，只为当前账户新增授权。
  - 收藏保留票的照片为原图，另记“浮雕输入资产”与封面；把“模型属于原图”的假设（第 3 节所列各处）改为“模型属于浮雕输入资产”。
  - 修改片名或放映时间触发重新检索与生成；外部请求设超时与有限重试，失败时退回票的照片并可重试。
- 验收：用固定响应样例覆盖 TMDB 命中、同名多部选择、片名不一致不匹配、无 Key 走维基百科、两者都无结果用票的照片；同一影片第二次不再请求外部；卡片封面为海报、详情可看原图；页面显示来源与“仅限小范围非商用测试”；同步拉取包含海报资产；CI 不访问真实 TMDB 或维基百科。
- 不做：演职员、简介等详情抓取。

### WP-06 徽章素材库规范与校验

- 目标：定义素材库目录、清单与校验，用户生成素材后可直接接入。依赖：无。
- 范围：新素材库加载与校验模块（参照 `template.py` 的 manifest 与 SHA 校验）、配置项 `MEMOVERSE_BADGE_LIBRARY_DIR`、`scripts/verify-badge-library.py`、后端测试（测试内生成微型合成素材库）、`backend/README.md` 配置表。素材文件不入 Git。
- 规范：见 4.1，属于可调整的默认值。
- 验收：合法库通过；缺文件、SHA 不符、尺寸或格式不符、ID 重复、映射指向清单中不存在的 `cityId`、缺字体、通用图案或稀有度边框时明确报错；库无效时徽章功能不可用并显示原因，其他功能正常。
- 不做：生成素材本身（由用户用 GPT 生图完成并审核）。

### WP-07 徽章生成与浮雕

- 目标：交通票生成双城徽章浮雕。依赖：WP-04、WP-06。
- 范围：新徽章模块（抽取、图层合成、分层高度网格与 GLB 导出）、生成流水线分支、`store.py`（抽取结果）、`state.py`、`backups.py`、前端卡片封面与详情（城市、稀有度、原图入口）。
- 约束：GLB 导出沿用 `anyimage_worker.py` 的网格与 trimesh 写法，并以同样的子进程边界运行；产物沿用 `models/<id>/` 三件套与 `validate_model_outputs`（若须调整校验，同步备份恢复）。抽取使用服务端随机种子，持久化种子与结果，同一输入版本重放结果一致；用户修正站点、城市或乘车日期后重新抽取；未覆盖城市用通用徽章；缺出发或到达城市时不生成徽章，用票的照片做浮雕与封面。
- 验收：珠海→北京同时含两城元素；卡片封面为徽章、详情可看原图；重新打开结果不变；修正城市后结果更新；缺一个城市时用照片，补填后生成徽章；未覆盖城市生成通用徽章；景区与展览门票不生成徽章；同步拉取包含徽章资产；固定种子抽样 10,000 次，各稀有度频率与配置概率相差小于 1 个百分点；GLB 在 Web 查看器正常加载并遵守 40°；不调用任何生图接口。
- 不做：稀有度防刷、徽章交换。

### WP-08 节日特效

- 目标：票面日期落在节日或其法定假期内时，海报与徽章带节日特效（主文档 3.8）。依赖：WP-05、WP-07。
- 范围：节日判定模块（农历与节气换算库、历年法定假期数据，如 `chinesecalendar`，均固定版本，许可写入 `THIRD_PARTY.md`）、海报边框层与徽章节日图层、素材库清单的节日部分。
- 约束：海报的节日边框在 AnyImage 网格之外单独建模，不参与深度估计；徽章的节日元素按图层高度加入；不做查看器动画。
- 验收：十个节日的当天判定与权威日历在 2025—2030 年对照一致；法定假期整段生效（含中秋与国庆连休时节日当天优先）；数据未覆盖的年份只算当天；元宵、七夕、圣诞只算当天；非节日与退回票照片时无特效；修改票面日期后特效随之更新，修改收藏日期不影响。
- 不做：查看器动画、粒子与光效。

### WP-09 徽章墙

- 目标：“我的”页显示已收集的城市元素与各稀有度数量。依赖：WP-07。
- 范围：`state.py` 或新的只读接口、`demo/src/Prototype.tsx` 的 profile 路由与新展示组件、Web 分享页与探索页的“示例”标识、Web 测试。
- 验收：数据只来自当前账户的徽章收藏；删除收藏后计数更新；空状态正常；分享与探索的初始内容显示“示例”标识；360、390、768、1280 宽度无横向溢出。
- 不做：排行、分享徽章墙。

### WP-10 Android 工程骨架与本地优先存储

- 目标：可安装的 Kotlin + Compose App：登录、按账号隔离的本地库与文件、拍照与导入保存。依赖：WP-01、WP-02。
- 范围：新目录 `android/`（Gradle Kotlin DSL，依赖固定版本）、`.github/workflows/` 新增 `Android tests`（构建与单元测试）、`AGENTS.md` 与项目运行信息的合并检查清单、`README.md`（技术栈表、CI 表、Android 构建与安装说明；不新建 `android/README.md`）。
- 约束：Android SDK、JDK 与 Gradle 缓存放 D 盘（`ANDROID_SDK_ROOT`、`GRADLE_USER_HOME`）；Room 与文件目录按用户 ID 分区；会话凭据用 Android Keystore 加密保存；邮箱与 Google 登录走 WP-02 接口；服务器地址由构建配置注入，开发时模拟器经 `10.0.2.2` 访问本机后端；minSdk 默认 26，用户告知真机版本后调整。
- 验收（自动化）：存储、账号隔离与登录状态的 JVM 或 Robolectric 测试；CI 通过。验收（用户真机）：首次必须登录；断网可新建、编辑，重启后仍在；换号后看不到前一账号数据，且前一账号数据仍保留。
- 不做：同步（WP-13）、近场（WP-14）。

### WP-11 Android 界面与浮雕查看器

- 目标：按 V1–V5 实现收藏首页、分类、探索（示例）、朋友分享、我的（含徽章墙）、详情与编辑；原生浮雕查看器。依赖：WP-10。
- 范围：`android/` 界面与查看器模块；参考图 `docs/design-references/`。
- 约束：查看器用 Filament 或基于它的 SceneView 加载同一 GLB；总偏转不超过 40°、触点所在的边角下压，逻辑与 `demo/src/relief-angle.ts` 一致并有单元测试；生成状态（二维、处理中、就绪、失败）真实可见。
- 验收（自动化）：查看器角度与方向单元测试；Compose 界面测试覆盖五个页面的结构、无模型时显示封面或原图。验收（用户真机）：页面与 V1–V5 对照；浮雕倾斜与按压手感；离开页面后不卡顿。
- 不做：探索的真实推荐与社区发布。

### WP-12 Android 离线 OCR

- 目标：断网时识别简体中文与英文字母，自动填写收藏日期（主文档 3.4、D-065）。依赖：WP-10。
- 范围：`android/` 识别模块与编辑页。
- 约束：使用 ML Kit 中文文字识别的捆绑模型，不依赖 Play 服务；只填收藏日期，来源记为离线识别；识别文字只在编辑页临时显示供复制，不写入数据库或日志；不做自动分类。
- 验收（自动化）：日期提取规则的单元测试（用 WP-04 的文本夹具）；离线识别的字段同步后被服务端结果覆盖，用户填写的不被覆盖。验收（用户真机）：飞行模式下样例票据填出日期；识别失败不阻止保存。
- 不做：离线浮雕生成、离线分类。

### WP-13 Android 同步接入

- 目标：本地修改进入 Outbox，联网后由 WorkManager 上传与拉取，并下载完整本地副本。依赖：WP-01、WP-11。
- 范围：`android/` 存储与同步；服务端只在发现 WP-01 缺陷时修改并补测试。
- 约束：本地修改与 Outbox 写入同一 Room 事务，Outbox 只记录改动的字段；先上传图片再提交新建操作；上传后以服务端返回值更新本地；收到墓碑删除本地记录；下载原图、模型与派生资产形成完整副本；未同步内容不被清理；清理缓存只删临时文件。
- 验收（自动化）：Outbox、重放幂等、墓碑处理与断点恢复的 JVM 测试，连接本机后端的集成测试；两台 App 设备改同一字段时以后到服务器的为准，改不同字段时都保留。验收（用户真机）：断网新建、编辑、删除，联网后 Web 可见且一致；删除后旧设备上线不复活；同步中途断网可恢复且不重复创建；空间不足时显示未完成。
- 不做：实时推送。

### WP-14 近场分享

- 目标：两台 Android 在无互联网时分享收藏，规则按主文档 3.11。依赖：WP-13；协议语义参照开题 A §6（`docs/sources/电子票根收藏与离线分享_开题报告.docx`）。
- 范围：`android/` 新模块（纯 Kotlin 协议核心、Wi-Fi Direct 发现与连接、前台服务传输、导入）；服务端同步扩展“收到的分享”（`services/sync.py`、`services/social.py`），模型按 `models/` 三件套传送并经 `template.validate_model_outputs` 校验；协议规格写入 `docs/近场分享协议.md`（本计划指定的唯一新增文档）。
- 约束：一套版本化协议，含版本协商、提议、接收或拒绝、清单、续传偏移、数据帧、校验、提交、回执、取消与错误；带长度前缀的 JSON 加二进制帧；限制包大小、文件数、类型与路径；TCP 链路使用 TLS，配对时用二维码或短码核对对端公钥指纹；原票照片默认不在发送清单中。
- 验收（自动化）：JVM 回环测试覆盖正常传输、拒绝、取消、断开后续传、损坏文件校验失败不导入、重复包不重复导入、版本不兼容在协商阶段拒绝、公钥指纹不符时拒绝连接；收到的分享同步后 Web 分享页可见。验收（用户）：两台真机按 PR 中的测试清单执行。
- 不做：iOS、跨公网、多人 P2P、Nearby。

### 4.1 徽章与素材库默认值（可调整）

- 稀有度概率：普通 60%、稀有 25%、史诗 12%、传说 3%。
- 视觉：普通为哑光浅色边框；稀有为银色金属边框；史诗为金色金属边框加浮雕纹样；传说为镭射彩虹边框。差异只由边框素材与 GLB 材质（金属度、粗糙度）表现，不需要额外城市元素。
- 覆盖：4 个直辖市、27 个省会与自治区首府、5 个计划单列市（大连、青岛、宁波、厦门、深圳）及珠海，共 37 城；每城地标、美食、文化三类元素各 2 个变体，另配一套配色。其他城市在清单中只登记 `id`、`name`、`palette`（不含 `elements`），用于站名映射与通用徽章。
- 文件：PNG，透明背景，1024×1024，sRGB，单个不超过 1 MB；扁平插画或珐琅徽章风格；图中不含文字，城市名由程序用素材库中的中文字体排版（如 OFL 许可的 Noto Sans SC）。`festivals/` 的装饰同时用于海报边框与徽章图层。
